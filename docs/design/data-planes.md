# 数据平面与丢失语义

Purser 把“资源是什么”和“资源现在被谁占着”拆成两个平面。理解这两个平面各自的权威范围，才能正确选择后端、备份策略与 Redis 部署方式。

| 平面 | 实现 | 保存内容 | 谁是权威 |
| --- | --- | --- | --- |
| 存储层（storage） | `memory` / `sqlite` / `mysql` | 资源主数据、重要状态、槽位计数、`version` CAS、审计 | 长期权威；丢失即业务事故 |
| 协调层（coordination） | `memory` / `redis` | 在途租约、心跳、等待唤醒、校验缓存 | 运行期租约权威；对账后与存储槽位一致 |

两个平面独立取值，行为测试按 存储 × 协调 的笛卡尔积运行。参见[架构](architecture.md)与[多实例部署](../guides/multi-instance.md)。

## 三类“丢失”不是一个严重级别

这是最容易误读的地方：文档过去把协调层丢失笼统写成“只影响调度准确性”。实际上要分三种情况：

### 1. 存储层丢失：业务事故

资源 ID、类型化 payload、状态、配额、密文、审计都在存储里。丢失后无法从协调端重建，只能靠[备份与恢复](../guides/operations.md)。

- `sqlite` 适合单机持久化，仍需备份文件。
- `mysql` 适合已有数据库基建的多实例部署。
- 备份文件是**明文**的（敏感字段在库内加密，导出时解密），必须按敏感数据保管。

### 2. 单实例丢失协调层数据：可对账收敛

协调端清空或重启后，`Pool.start()` 会读取协调端当前存活租约，并按槽位之和重设存储里的占用计数：

- 全孤儿（没有存活租约但存储仍有占用）→ 归零；
- 部分孤儿（部分租约存活）→ 按存活租约之和收敛；
- 资源主数据不受影响；
- 迟到 release（token 已不在协调端）幂等，不会误扣新持有者槽位。

这类丢失影响的是“这一刻的调度准确性”，恢复后可以收敛。

### 3. 多实例丢失协调层数据：可能重复占用

多实例共享同一个 Redis 时，如果 Redis 丢失在途租约：

- 实例 A 仍在用资源 R，但协调端已经没有 A 的租约记录；
- 实例 B 查询时看不到占用，会再次分配 R；
- 结果是**同一资源被两个消费者并发使用**。对代理/账号来说，这可能导致封号、风控或数据串用。

对账只能修正槽位计数，无法追回已经被“重复分配”的那段时间。因此：

!!! danger "协调 Redis 必须按持久化组件部署"

    开启 AOF（推荐 `appendfsync everysec` 或更强）或等价的持久化策略，并纳入备份/高可用方案。不要把协调 Redis 当纯缓存，也不要随意 `FLUSHDB`——丢失在途租约会导致同一资源被并发使用。

单实例使用 `sqlite + memory` 或 `mysql + memory` 时没有跨实例可见性问题，但协调记录只存在于进程内，重启即清空。

## 事件历史是第三种数据

事件总线是进程内有界环形缓冲（默认 10 000 条），保存最近事件供 SSE 游标续传与历史回放。它既不进存储，也不进协调端：

- 进程重启后历史清空，客户端需要重新以 `after_seq=0` 订阅；
- 容量溢出时只逐出最旧事件，慢订阅者会丢弃并告警；
- 需要长期审计时使用审计日志（`PURSER_AUDIT_PATH`），不要依赖事件历史。

## fail-closed 与对账时机

- 协调端连接或操作失败时抛 `BackendUnavailable`，不会静默降级为本地内存状态。宁可暂时不可用，也不产生无法对账的分裂视图。
- Redis 连接与操作带 5 秒超时，并强制 RESP2 以兼容 Redis < 6。
- 对账发生在池启动时；运行期间协调端与存储的短暂不一致由每次租约/槽位的 CAS 与幂等归还保证，不会周期性地“全量重算”。
- 槽位硬不变量：`0 <= used_slots <= max_slots`，跨后端、跨实例成立。

## 选型与自检

| 场景 | storage | coordination | 必须做的事 |
| --- | --- | --- | --- |
| 本地开发/测试 | `memory` | `memory` | 接受重启即清空 |
| 单机持久化 | `sqlite` | `memory` | 备份数据库文件 |
| 单实例服务 | `sqlite` / `mysql` | `memory` | 备份数据库；重启后等待对账 |
| 多实例服务 | `sqlite` / `mysql` | `redis` | Redis 持久化、独立 DB、监控断连 |

上线前至少确认：

```bash
curl http://127.0.0.1:8000/readyz
curl http://127.0.0.1:8000/service   # 每个实例的 storage / coordination 是否一致
```

并验证 Redis 的持久化配置确实生效，而不是只看到 `PURSER_REDIS_URL` 能连通。
